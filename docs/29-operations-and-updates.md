# E4 운영 점검·업데이트·장애 대응

작성일: 2026-10-31 (Asia/Seoul). E1~E3 도구를 연결한 운영 절차다. 실제 NAS 접속·HTTPS/실물 기기·예약 백업/외부 사본 설정은 여전히 현장 검증 대상이며 이 문서로 완료 처리하지 않는다.

## 평상시 점검

Python 3.11 이상, 로컬 Docker 소켓 접근과 Compose v2가 필요하다.

```sh
python3 scripts/check-operations.py \
  --env-file /absolute/path/production.env \
  --project member-app \
  --disk-path /volume1/docker/member-app \
  --backup-directory /volume1/private/member-backups \
  --expect-app-image member-app:RELEASE
```

컨테이너 생성·재시작·마이그레이션·DB 쓰기·이미지 교체를 하지 않는 읽기 전용 검사다. 환경변수·secret·health 로그 본문은 출력하지 않는다. JSON에는 서비스별 상태·health·종료 코드·재시작 횟수·OOM·이미지 참조/ID, 디스크 여유 공간, 백업 검사 결과만 담는다.

- db/app은 running+healthy, migrate는 exited+0이어야 한다. 누락·중복·실패·OOM은 종료 코드 1이다. migrate의 완료 후 종료는 정상이다. 재시작 횟수는 경고로 표시하고 직전 관측보다 늘어나는지 확인한다.
- 기본 여유 공간 기준은 지정한 파일시스템의 2GiB다. `--min-free-gib`로 조정한다. DB volume과 백업이 다른 볼륨이면 각 경로에서 따로 검사한다. Docker 데이터가 있는 파일시스템도 별도로 확인한다. 이 수치는 DB 증가량·백업·새 이미지 필요 용량을 보장하지 않는다.
- `--expect-app-image`는 실제 컨테이너 이미지 참조와 일치 여부를 검사한다. 변할 수 있는 태그만으로 동일 바이너리를 보장하지 않으므로 출력한 imageId를 릴리스 기록과 대조한다. 실제 운영에는 버전별 불변 태그 또는 digest를 사용한다.
- 백업 경로를 주면 E3 이름 규칙에서 가장 최신 이름의 manifest/dump 쌍을 검사한다. 기본 최대 나이는 26시간이며 `--max-backup-age-hours`로 조정한다. 미래 시각·누락·손상·열린 파일 권한도 실패다. `.partial`을 성공한 백업으로 취급하지 않는다. 시각 비교는 manifest의 시간대를 사용한다.
- 백업 경로를 생략하면 해당 검사는 `not-checked`와 경고로 표시한다. `runtime-ok`는 실행 상태 점검 범위의 결과이며 운영 준비 전체의 완료를 뜻하지 않는다. 해시 일치도 복원 연습·NAS 외부 사본의 존재를 증명하지 않는다.

공개 경로는 [E2](27-nas-https-installation.md)의 `check-deployment.py`로 따로 검사한다. 매일 점검 결과와 백업 작업 종료 코드를 확인하고, 외부 사본·정기 복원 연습을 [E3](28-backup-and-restore.md)에 따라 수행한다. 관측 결과를 보관한다면 운영 경로·이미지 정보가 포함됨을 고려해 접근을 제한한다. 모니터링 예약·외부 알림 전송은 아직 설정하지 않았다.

## 업데이트 전후 절차

1. 현재 앱/tools의 불변 이미지 참조·실제 imageId, 소스 커밋, 마이그레이션 버전, 운영 설정 버전을 기록한다. 미커밋 작업 트리를 배포 가능한 릴리스로 간주하지 않는다. 비밀키 값은 릴리스 기록에 적지 않는다.
2. 변경 내용을 검토하고 이전 앱과 새 DB 스키마의 호환성을 확인한다. 새 앱/tools 이미지를 먼저 준비한다. 레지스트리 사용 시 인증된 pull, 오프라인 전달 시 이미지 load 후 imageId를 대조한다. 이 문서의 작성 과정에서는 이미지를 푸시하거나 실제 NAS를 업데이트하지 않았다.
3. 기존 운영 설정으로 E4 점검과 E2 HTTPS 점검을 수행한다. E3 새 백업 → 별도 복원 연습 → NAS 외부 사본 확인을 마친다. 실패하면 업데이트를 중단한다.
4. 사용자가 입력 초안을 저장/정리할 시간을 주고 유지보수 시간을 정한다. 앱 쓰기를 중단한 뒤 최종 백업을 확보한다. DB를 중지하거나 volume을 지우지 않는다.
5. 운영 설정의 APP_IMAGE와 TOOLS_IMAGE를 검증된 새 불변 버전으로 함께 바꾼다. E1의 전체 `docker compose ... up -d --wait`로 db healthy → migrate 성공 → app healthy 순서를 사용한다. 앱만 `--no-deps`로 교체하여 마이그레이션을 건너뛰지 않는다. 동일 태그를 재사용하면 변경 감지가 불명확하므로 피한다.
6. E4에 새 `--expect-app-image`를 지정해 확인하고 E2 공개 HTTPS·인증서·manifest/워커 검사를 실행한다. 두 계정의 격리, 실제 기록 저장·재조회, 설치 앱 재실행·입력 중 업데이트 보호를 합성 확인용 기록으로 검증한다. health만 성공한 상태로 정상 운영을 선언하지 않는다.
7. 확인된 릴리스·백업·검증 결과·소요 시간을 기록하고 유지보수를 종료한다. 이전 이미지·설정·백업은 보관 정책에 따라 유지한다.

업데이트 실행 명령은 [E1](26-docker-production.md)의 실제 환경 파일 경로와 프로젝트 이름을 사용한다. 운영 변경은 현장 담당자가 검토한 릴리스에 대해 실행한다. 자동 배포나 자동 롤백은 구현하지 않았다.

## 실패 시 대응

| 증상 | 우선 확인과 대응 |
|---|---|
| Docker 연결 실패 | 로컬 소켓 권한·daemon 상태 확인. 다른 Docker context나 원격 daemon으로 임의 전환하지 않음 |
| DB unhealthy | 디스크·메모리·DB 로그·volume 경로 확인. 기존 데이터 보존, DB 초기화/volume 삭제 금지 |
| migrate 실패 | 앱 쓰기 유지 중단, 오류와 기존 migration 상태 확인. 임의 SQL 수정·실패 이력 강제 삭제·reset 금지 |
| app unhealthy | 이미지 참조, secret 파일의 소유 UID/0600·APP_URL·DB 연결 확인. 환경변수 전체 출력 없이 해당 설정만 확인 |
| 반복 재시작/OOM | 이전 관측과 재시작 증가량, 자원 사용·로그 회전 확인. 제한을 무조건 늘리기 전에 원인 확인 |
| 로컬 정상·공개 HTTPS 실패 | DSM 프록시 대상·DNS·인증서·방화벽·캐시 확인. TLS 검증을 꺼서 우회하지 않음 |
| 백업 누락/오래됨/손상 | 새 백업과 격리 복원부터 재시도. 기존 마지막 정상 사본을 지우지 않음 |
| 새 버전 오류 | 호환 가능한 DB 변경일 때만 이전 앱/tools 참조로 되돌리는 계획 수립. DB downgrade를 자동 실행하지 않음 |

DB 변경이 이전 앱과 호환되지 않으면 새 별도 DB로 검증된 백업을 복원하고 앱 연결을 전환하는 복구 계획이 필요하다. 백업 이후 기록 손실 범위를 먼저 확인한다. 원래 DB를 덮어쓰는 복구는 현재 도구에서 제공하지 않는다. 실제 복구와 기존 DB 삭제는 별도 검토 대상으로 남긴다.

로그를 확인할 때에는 필요한 서비스·시간대·줄 수만 제한해 확인하고, 공유하기 전에 이메일·쿠키·토큰·DB URL 등 개인 정보와 비밀값을 제거한다. 도구가 정상이어도 사용자 기록 오류·소유권·장비/좌우 의미는 별도 검증해야 한다.

## 검증 범위

`npm run test:operations`는 서비스 누락/중복·unhealthy·마이그레이션 실패/진행 중·OOM·재시작 경고, 백업 시각·손상·권한·쌍 누락을 검증한다. `npm run test:docker`는 E1의 실제 격리 Compose에서 새 점검 CLI가 성공하고 완료된 migrate를 정상 처리하는지 확인한다. 실제 NAS 업데이트·모니터링 예약·장애 복구 훈련은 아직 하지 않았다.

2026-10-31 운영 검사 테스트 3개, 실제 Docker smoke, TypeScript·diff 검사 통과. 합성 테스트 자원은 종료 시 정리했고 기존 개발/테스트 DB를 유지했다.
