# E3 PostgreSQL 백업·복원 검증

작성일: 2026-10-31 (Asia/Seoul). Python 3.11 이상과 로컬 Docker 소켓, Compose v2가 필요하다. 운영 DB를 덮어쓰는 복구 명령은 제공하지 않으며, 별도 임시 DB에서 복원 가능한지 확인한다. 실제 NAS 스케줄·NAS 외부 사본은 현장 설정 대상이다.

## 백업

E1 운영 Compose의 실행 중인 db 컨테이너에서 `pg_dump --format=custom`을 실행한다. 컨테이너 내부 Unix socket을 사용하므로 호스트에 DB 포트를 개방하거나 비밀번호를 인자로 전달하지 않는다. 애플리케이션을 중단하지 않는 일관된 DB snapshot이다. DDL 마이그레이션과 백업 실행 시간은 겹치지 않도록 운영한다.

```sh
python3 scripts/database-backup.py backup \
  --env-file /absolute/path/production.env \
  --project member-app \
  --directory /absolute/path/private-backups
```

디렉터리는 없으면 0700으로 생성하며 기존 디렉터리가 다른 계정에 열려 있으면 거부한다. NAS 공유 폴더 ACL에서도 접근 계정을 제한해야 한다. UTC 시각과 UUID를 포함한 파일 이름을 사용하며 같은 이름을 덮어쓰지 않는다. 임시 `.partial`에 스트리밍 후 성공 시 `.dump`로 확정하고, `.json`에 생성 시각·크기·SHA-256을 기록한다. 파일 권한은 0600이다. 실패하면 이번 실행의 부분 파일을 제거한다. 중단·정전으로 남은 partial은 유효한 백업으로 사용하지 않는다.

dump에는 모든 계정·암호 해시·세션·개인 운동 데이터가 포함된다. 평문 데이터 파일이므로 암호화된 저장소와 전송을 사용한다. JSON 해시는 전송 손상 감지용이며 공격자에 대한 진본성 보증은 아니다. dump와 JSON을 한 쌍으로 보관한다. Git과 Docker 컨텍스트에서 backups·dump·partial을 제외했다.

## 복원 연습

출력된 dump 경로로 실행한다. PostgreSQL 17 고정 이미지는 E1과 같은 digest이며 로컬에 없으면 미리 준비한다.

```sh
python3 scripts/database-backup.py restore-check /absolute/path/private-backups/member-TIMESTAMP-UUID.dump
```

해시·크기를 검증한 뒤 UUID 이름의 새 PostgreSQL 컨테이너를 만든다. 외부 네트워크·공개 포트·named volume 없이 tmpfs에 복원하고, `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`로 스키마·데이터·제약을 복구한다. public 테이블 행 수만 출력하며 개인 행 내용은 출력하지 않는다. 종료 시 자신의 임시 컨테이너를 제거한다. 임시 DB의 trust 인증은 외부 접근이 없는 연습 컨테이너에만 사용한다.

복원 컨테이너 메모리는 1GiB, 데이터 tmpfs는 768MiB로 제한한다. 큰 백업은 이 한도를 초과할 수 있으므로 실패를 손상으로 단정하지 않는다. 각 Docker 명령 제한은 10분이다. 실제 데이터가 커지면 용량·시간을 검토한 별도 격리 복원 환경으로 확장한다. SIGKILL·호스트 종료 시 UUID 컨테이너가 남을 수 있으며 확인 후 해당 컨테이너만 정리한다. `docker volume prune`이나 운영 `down -v`로 정리하지 않는다.

이 연습은 데이터베이스 파일·제약을 복원할 수 있는지 확인한다. 앱 버전과의 호환성·브라우저 로그인·권한은 복원 DB를 연결한 별도 앱에서 추가 검증해야 한다. 운영 DB 연결을 바꾸거나 기존 DB를 삭제하는 명령은 수행하지 않는다.

## NAS 운영 정책

- DSM 작업 스케줄러에서 운영 계정으로 매일 새벽 백업 명령을 실행한다. 절대 경로와 로컬 Docker 권한을 확인하고 겹치는 실행을 막는다. 스케줄러 등록·실패 알림은 아직 실제 NAS에 적용하지 않았다.
- 초기 보관 기준은 일별 7개·주별 4개·월별 3개다. 보관량과 운동 기록 손실 허용 시간을 보고 조정한다. 이 단계에서 자동 삭제는 구현하지 않았다. 최신 검증 성공본과 NAS 외부 사본을 확보한 뒤 오래된 쌍을 검토해 삭제한다.
- 백업 직후 JSON 해시 확인과 복원 연습을 실행한다. NAS와 독립된 암호화 저장소에 사본을 전송하고, 전송된 사본의 해시를 비교한다. 외부 저장소·키·업로드·삭제 작업은 아직 설정하지 않았다.
- 목표 RPO는 초기 24시간이다. 실제 복원 시간을 기록하기 전에는 RTO를 보장하지 않는다. 한 달에 한 번, 그리고 스키마/이미지 업데이트 전후에 복원 연습을 수행한다.
- DB dump는 컨테이너 이미지, Compose/프록시 설정, DB 비밀번호·인증 secret을 포함하지 않는다. 앱 소스 커밋·이미지 digest와 운영 설정·비밀키는 접근을 분리한 암호화 저장소에 별도로 보관한다. 같은 디렉터리에 평문 비밀키를 복사하지 않는다.

## 장애 복구 순서

1. 앱 쓰기를 중단하고 현재 DB·로그를 보존한다. 원인과 호환되는 이미지/스키마 버전을 확인한다.
2. 검증된 dump·JSON을 NAS 외부 사본에서 가져와 임시 환경에서 복원한다.
3. 별도 새 영구 DB에 복원하는 변경 계획을 준비한다. 소유자·DB 비밀번호·앱 버전·마이그레이션 호환성을 확인한다. 기존 운영 DB는 덮어쓰지 않는다.
4. 별도 앱에서 계정 접근·소유권·운동 세트·좌우/NULL/0·이전 기록을 검증한 후 접속 전환한다. 복원한 과거 세션을 계속 허용할지 결정하고 필요하면 인증 secret을 교체한다.
5. HTTPS·설치 앱 재실행과 새 기록 저장을 확인하고 실제 복구 시간을 기록한다. 이전 DB 제거는 보관 기간과 별도 승인 후 진행한다.

## 자동 검증

```sh
npm run test:backup
```

합성 컨테이너에 현재 실제 마이그레이션 DDL 전체와 두 소유자의 Unicode/NULL/0/소수 fixture를 생성하고 dump → 임시 컨테이너 복원을 실행한다. 복원 후 fixture의 원래 값과 외래키 관계를 검사하고 테이블 행 수와 앱 테이블 존재를 확인한다. 파일 0600·체크섬 손상 거부·실패한 dump의 partial 정리·공개 디렉터리 거부도 확인한다. 기존 개발·테스트·운영 DB는 건드리지 않는다.

2026-10-31 Docker 통합 검증 1개 통과(실패 0). 현재 앱 스키마 DDL 전체와 합성 fixture를 사용한 결과이며 실제 운영 데이터 복원·NAS 외부 사본 전송 결과를 대신하지 않는다.
