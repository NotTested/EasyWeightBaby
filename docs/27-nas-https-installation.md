# E2 NAS HTTPS·브라우저·설치 검증

작성일: 2026-10-30 (Asia/Seoul). E1 이미지를 DSM 기본 역방향 프록시 뒤에서 운영하는 기준 절차다. 운영 도메인·NAS 접속 정보가 아직 없으므로 실제 NAS 배포 완료를 뜻하지 않는다.

## 기본 구성

브라우저와 설치 앱은 같은 주소 `https://workout.example.com`을 사용한다. 이 이름은 예시이며 실제 도메인으로 바꾼다. `/workout` 같은 하위 경로 배포는 현재 지원하지 않는다.

```text
브라우저 / Chrome 설치 앱
         │ HTTPS :443 (유효한 도메인 인증서)
         ▼
DSM 역방향 프록시
         │ HTTP 127.0.0.1:3000
         ▼
Compose app ── 내부 네트워크 ── PostgreSQL (외부 포트 없음)
```

E1의 `APP_BIND_ADDRESS=127.0.0.1`을 유지한다. DSM 호스트 프록시는 NAS loopback의 앱에 연결한다. 다른 컨테이너에서 프록시를 실행한다면 컨테이너의 127.0.0.1은 NAS가 아니므로 이 구성을 그대로 사용하지 않는다. 해당 경우에는 app의 frontend 네트워크를 프록시에 연결하고 앱 호스트 포트를 제거하는 별도 구성이 필요하다. PostgreSQL backend는 프록시에 연결하지 않는다.

## DSM 설정 순서

1. 전용 도메인의 DNS를 접속 가능한 NAS 주소에 연결한다. 외부 접속이면 공유기·방화벽에서 필요한 HTTPS 443 경로를 준비한다. 내부망 전용이면 내부 DNS와 신뢰 가능한 도메인 인증서를 준비하며 외부 포트 개방은 필요하지 않다. LAN·모바일에서 같은 도메인을 사용한다. DSM 관리 포트나 DB 포트를 앱용으로 개방하지 않는다.
2. DSM 제어판의 보안 → 인증서에서 해당 도메인의 유효한 인증서를 준비하고 이 프록시 서비스에 연결한다. 인증서 발급 방식에 따라 HTTP 검증 또는 DNS 검증 절차가 다르다. 브라우저 경고를 무시하는 방식으로 설치를 진행하지 않는다.
3. 로그인 포털 → 고급 → 역방향 프록시에서 소스를 HTTPS, 실제 도메인, 443으로 설정하고 대상을 HTTP, `127.0.0.1`, E1의 `APP_PORT`(기본 3000)로 설정한다. DSM 버전에 따라 메뉴 이름은 다를 수 있다.
4. 원래 공개 Host를 보존하고 `X-Forwarded-Proto: https`, `X-Forwarded-Host: 실제 도메인`을 전달한다. 외부 요청이 보낸 전달 헤더는 프록시가 신뢰 가능한 값으로 덮어쓰도록 한다. 접근 제어·속도 제한에서 사용할 클라이언트 IP 전달 체인도 확인한다.
5. 프록시의 로그인 강제 전환·캐시·본문 변경 기능을 앱 경로에 적용하지 않는다. `/api/*`, HTML/RSC, `/sw.js`를 캐시하지 않고 앱의 Cache-Control을 보존한다. manifest·아이콘·워커는 로그인 없이 원래 경로로 제공해야 한다. Next.js 응답을 버퍼링하는 프록시는 스트리밍 지연이 없는지도 확인한다.
6. E1 설정의 `APP_URL`을 같은 HTTPS 원점으로 설정하고 앱을 재생성한다. 공개 HTTPS와 내부 HTTP를 혼동하여 APP_URL을 내부 주소로 바꾸지 않는다. 인증 Origin과 Secure 쿠키가 공개 주소를 기준으로 동작한다.

설정과 실행은 [E1 문서](26-docker-production.md)를 따른다. HTTP 주소도 제공한다면 프록시에서 정규 HTTPS 주소로 전환한다. HTTPS가 안정된 뒤에만 HSTS 정책을 검토하며 다른 NAS 서비스에 영향을 주는 전역 정책을 임의로 적용하지 않는다.

## 배포 후 익명 점검

NAS 또는 같은 접속 경로의 PC에서 Python 3로 실행한다. 표준 라이브러리만 사용하며 계정·비밀번호·DB 접속 정보는 필요하지 않다.

```sh
python3 scripts/check-deployment.py https://workout.example.com
```

검증 대상은 TLS 인증서·DB health·미인증 `/api/me` 차단·로그인 HTML·manifest의 안정적인 id/scope·PNG 아이콘·캐시 금지 서비스 워커다. 로그인 페이지로의 강제 리다이렉트도 실패로 처리한다. GET 요청만 보내며 DB 쓰기·로그인·설치는 하지 않는다. 기존 프록시 환경변수와 시스템 인증서 신뢰를 사용한다. 내부 CA를 정식으로 사용하는 환경은 `DEPLOY_CA_FILE=/absolute/path/ca.pem`으로 추가 신뢰할 수 있다. 인증서 검증을 끄는 옵션은 없다.

성공 메시지는 실제 Chrome 설치 또는 계정 동작까지 검증했다는 뜻이 아니다. 아래 현장 검증도 필요하다. 외부에서 성공해도 내부 DNS/hairpin 문제로 LAN에서 실패할 수 있으므로 각 네트워크에서 반복한다.

## Chrome 현장 검증표

| 확인 | 방법과 통과 기준 |
|---|---|
| 브라우저 접근 | 일반 창에서 인증서 경고 없이 로그인 화면과 모든 자원이 열림. 개발자 도구에 mixed content 오류 없음 |
| 로그인·쿠키 | 초대한 계정으로 로그인. 세션 쿠키 Secure·HttpOnly·SameSite=Lax 확인. 토큰 값을 복사하거나 기록하지 않음 |
| 직접 주소 | 로그인 후 `/settings`, `/history` 직접 열기·새로고침 정상. 비로그인 개인 화면 접근은 로그인 안내 |
| PC 설치 | Chrome 설정 화면의 설치 동작 또는 브라우저 설치 메뉴로 설치. 이미 설치된 경우 기존 앱 상태 확인 |
| 앱 창 실행 | 설치 앱 실행 후 설정에 ‘설치된 앱으로 사용 중’ 표시. 로그인 유지·메뉴 이동·종료 후 재실행 정상 |
| 모바일 | Android Chrome에서 같은 HTTPS 주소로 접속·설치·재실행 확인. iOS는 Safari 홈 화면 추가를 별도 확인 |
| 실제 기록 | 합성 확인용 운동 시작·세트 저장·새로고침·종료 후 기록 확인. 다른 계정에서 보이지 않음 |
| 연결 끊김 | 공개 오프라인 안내와 미전송 입력 안내 확인. 자동 서버 저장·완전 오프라인 사용으로 안내하지 않음 |
| 업데이트 | 입력 중 앱 업데이트를 적용하면 입력 보호 안내. 저장/정리 후 명시적으로 적용 가능 |
| NAS 재시작 | 컨테이너 재시작 후 health 정상, 계정·기록 유지. 앱 재실행 정상 |

설치 메뉴가 없으면 비공개 창 여부·기존 설치·보안 연결·manifest/아이콘/워커 응답·관리 정책을 확인한다. 설치 없이 브라우저로도 사용할 수 있다. 설치 앱 제거는 서버 계정·기록 삭제가 아니다.

## 이번 환경의 검증과 남은 조건

로컬 신뢰 HTTPS 프록시에서 자동 점검 도구, Secure/HttpOnly/SameSite 쿠키, 외부 Origin의 로그아웃 요청 거부, Chromium 실제 설치·standalone 딥링크·재실행을 검증했다. PWA 총 6개 통과(실패/건너뜀 0), TypeScript 검사 통과. HTTP 원점 거부도 확인했다. 테스트 CA만 잠시 신뢰하며 TLS 오류를 무시하지 않는다. 기존 테스트 DB의 합성 계정만 사용하고 종료 시 정리한다.

실제 NAS 도메인·인증서·라우팅·DSM 버전·실물 기기의 메뉴 설치는 이 결과로 대체하지 않는다. E2 현장 검증은 해당 정보와 접근 경로가 확보된 뒤 위 표를 실행해 완료한다. 그동안 E3 백업·복원 준비는 독립적으로 진행할 수 있다.
